# 原型与实现发现

## 初步原型发现
- 原型标题为“LazyMind · 消息通知与任务中心”。
- 定时任务支持“分组展示 / 逐条展示”。
- 任务组卡片用于组织任务并进入组内任务，不等同于一条可执行任务。
- 每个具体定时任务卡片拥有独立的“配置通知”入口。
- 原型文案明确区分：终端连接负责连接可用性，消息通知负责默认发送方式，任务中心负责“这项任务如何通知”。
- 任务组只承担组织、汇总、进入组内任务和删除组入口；原型明确写着“仅演示单个定时任务的消息提醒”。
- 任务组卡片没有“配置通知”入口；组内每条任务卡片各自拥有“配置通知”。
- 停用任务计划时通知配置保留。
- “清除任务通知配置”只将该任务规则置为未配置/关闭，不删除任务计划与历史发送记录。
- 任务通知编辑器可显式“使用全局默认”，但必须保存后才成为任务快照；不是持续动态继承。

## 当前假设
- 当前批量创建任务组 API 的每个任务不支持 notification 字段，组内任务只能静默初始化为全局默认。
- 当前前端只有单任务 `notificationDraft`，任务组的每个 `BatchScheduleDraft` 没有独立通知草稿与入口。
- 任务卡片操作区重复渲染了两次启用开关；原型只有一次。
- 正确主体应始终是具体 schedule/task ID；任务组仅影响列表筛选、批量创建和依赖组织。

## 最小兼容方案
- `BatchScheduleDraft` 增加可选 `notification`，每个任务独立保存。
- 批量创建后端事务在创建每个 schedule 后应用该任务自己的通知更新。
- 任务组创建弹窗的每个任务标签页增加“消息通知”入口，通知草稿写回当前 `client_key` 对应的任务。
- 没有显式修改通知时继续使用后端初始化的全局默认快照，保持旧客户端兼容。
- 删除任务卡片重复的启用开关。

## 待确认
- 任务组是否拥有独立通知规则，或仅聚合展示组内任务。
- 新建任务时默认通知规则如何从全局设置继承。
- 任务级清除覆盖后是恢复默认还是显式关闭。
