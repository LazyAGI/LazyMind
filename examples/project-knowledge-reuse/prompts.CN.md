# 中文复现提示词

[English](prompts.md) · [说明](README.CN.md)

这些是针对现有知策材料新增的复现提示词。将 `<KB_ID>` 替换为插件实际列出的专用知识库 ID，将 `<OUTPUT_DIR>` 替换为可写的绝对输出目录。先完成 README 中的建库和插件连接；不要把本文件上传进知识库。

## A — 方案摘要（新会话）

```text
请通过 LazyMind 插件，使用知识库 <KB_ID>（showcase-zhice-v1）中的 design.txt、prd.txt、review.txt、handoff.txt，为新加入项目的人生成“知策”方案摘要，保存为 <OUTPUT_DIR>/01-summary.md。
LazyMind 只负责检索与读取，正文由你写作。先列出该库文档确认身份，再检索并读取相关原文；不要从本地仓库读取材料，不做联网补充，不运行 Workflow。
摘要包括用户与任务、主要流程、角色边界、版本与导出规则、当前评审及交付状态。区分案例设定、提议规则、已验证事实和未知。每个关键结论给出实际读取的文档 ID、文件名和章节/条目；工具提供可打开的来源链接时保留它。
材料不足或互相不一致时如实指出，不自行补成已批准事实。文中引用但本次未提供的文件不能算你已读取的证据。最后列出实际检索、读取过的文档以及未能完成的步骤。
```

## B — 有依据的追问（同一会话）

```text
继续使用 LazyMind 插件检索、读取知识库 <KB_ID>。
评审中的 R-05 究竟指哪处范围变更表述？请对照产品方案和 PRD 的原文，说明研究启动前与启动后分别应如何处理，为什么当前写法可能被误读，以及它是否改变正式研发交付的阻塞状态。
把结果保存为 <OUTPUT_DIR>/02-scope-evidence.md。引用三份原文中的位置和实际文档 ID，区分原文规则、你的解释与尚未接受的决定。不要仅凭上轮摘要作答，不宣称已修复或已复验。
```

## C — 指定部分修改（同一会话）

```text
依据刚才通过 LazyMind 读取的材料，为 design.txt 中“改动范围后须重新确认”所在段落提出最小修改：明确启动前需要重新确认，启动后应创建新任务。
将原文片段、替换片段、来源位置和修改理由保存为 <OUTPUT_DIR>/03-design-revision.md。仅修改这段表述，其他内容、角色、数据政策和技术约束保持原样；以“修改建议，待确认”标记，不把 R-05 标为 resolved。
这是新建建议文件，不回写原文或知识库，不代表用户批准方案。检查替换是否引入来源未支持的规则，并报告检查结果。
```

## D — 新会话交接

在同一宿主新建空会话，只发送以下提示词。不附上 A–C 输出或前一会话摘要。

```text
请通过 LazyMind 插件使用知识库 <KB_ID>（showcase-zhice-v1）中的四份知策原始案例材料，为接手的产品、设计、研发、测试及业务/安全角色生成交接清单，保存为 <OUTPUT_DIR>/04-handoff.md。
先确认该库文档，再检索和读取原文；不要访问本地仓库、其他会话或联网补充，不运行 Workflow。
列出采用文件及版本、当前交付就绪状态、所有未解决的评审项及其级别、对应关闭条件、建议负责角色和所需证据。每个条目引用实际文档 ID、文件名和章节/编号。区分可展示、拟议规则、正式接受与测试通过，不虚构个人负责人或日期。
只能按当前知识库原文判断，不假定任何未写回材料的修改建议已生效。说明缺少哪些材料或验证，下一步需要谁确认什么，并列出实际读取的文件。
```

实跑注意：逐轮取证记录应区分本轮新读取和沿用上轮原文。`original_file.download_url` 是 API 下载地址，不应直接拼到网页域名当作原文页；找不到经过核实的网页链接时，保留文档 ID、文件名和章节即可。D 必须实际调用 `knowledge.search`，不能把列目录或读全文算作检索。已有失败及补验提示见实跑记录。
