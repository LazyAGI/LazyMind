[section-1] 1. 评审范围与标准
评审目标是判断是否可作为正式研发交付基线，不是判断演示是否好看。检查术语与状态、权限边界、需求和验收映射、原型覆盖、未决项、版本与审批状态。
已核对：产品方案、PRD 的静态内容与原型实现范围。界面验证记录随交付附上。未执行：真实用户测试、生产权限渗透测试、研究质量对照、全部 AC 端到端测试。
[section-2] 2. 可以复用的设计基础
三类角色、四个对象和任务/报告两类状态，在方案与 PRD 中保持同一主要含义。
PRD 列出 12 项 FR 和 18 项 AC，引用与风险场景可以定位。
方案明确公开资料、人工确认、版本保留、不对外发送，未把来源中的指令当作用户授权。
原型能演示部分主路径与恢复路径，并声明模拟数据、前端权限和内存状态的局限。
这些是内容和演示基础，不是已批准、已安全验证或已上线的证明。
[section-3] 3. 可定位的发现
ID / 级别	位置与证据	影响	最小修复与建议负责角色	复验方式
R-01 / P1	PRD §8 明确“补全的方案规则尚未确认”；权限表也标为提议	没有正式需求决策基线，研发无法区分不可变规则与设计建议	产品/业务负责人确认范围、角色与版本机制，记录决定及版本；角色待落实	检查接受记录，核对方案、PRD、原型使用同一规则
R-02 / P1	PRD §7–8 尚未确定保留期限、删除机制和敏感材料边界	真实企业数据的生命周期无法完整设计与验收	业务与安全负责人确定数据边界和删除/保留方式；不以“首版无删除入口”替代政策	补齐规则、权限与验收场景，再复核数据流程
R-03 / P1	PRD §7–8 说明性能、可用性、大小、成本和抓取可行性待定	无法对真实服务的可行性与非功能验收作出承诺	研发与产品确定允许来源、失败边界及测试目标；完成最小技术验证	提交验证结果与有依据的验收目标，检查范围是否需回改
R-04 / P2	原型 §3、§6 明确未覆盖 FR-012、服务端权限和并发冲突等	原型仅能作为部分体验示例，不能代替完整实现规格	设计与测试继续维护逐项覆盖表；优先补关键异常	走查补齐路径，并逐条区分“演示覆盖”和“验收通过”
R-05 / P2	方案 §3 写“改动范围后须重新确认”，PRD §3 写启动后改范围需新任务	脱离上下文阅读时可能把执行中改范围理解为原任务重确认	产品在方案该处补一句“启动前重确认；启动后创建新任务”	检查计划页及执行中改范围文案与 PRD 一致
R-01 至 R-03 是原稿已披露但尚未解决的门禁缺口，不是新发现的系统故障。没有已观察到的 P0 问题，不代表完成安全认证。

[section-5] 5. 结论与复验范围
本次结论为“退回修改”，适用目标是正式研发交付。因为存在未解决 P1，不使用“有条件通过”来暗示可先进入正式实施。
处理顺序：先接受或重开核心规则；再补齐数据政策和技术验证；同步澄清 R-05；最后按范围决定原型缺口的处理方式。修复后保留 R-01 至 R-05 编号，状态从 not-resolved 变为 resolved、partially-resolved 或 not-retested，并检查受影响区域的回归。
当前五项均为 not-resolved。未收到真实负责人确认、未修改上游文件、未执行正式复验；后续阶段只提供 blocked 的交付整理示例。
