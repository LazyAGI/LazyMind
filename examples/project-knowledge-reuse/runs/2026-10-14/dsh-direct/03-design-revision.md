## 4. 修改理由

1. **消除已记录的歧义**。`review.txt` `[section-3]` 第 51 行 `R-05 / P2` 指出：方案写“改动范围后须重新确认”，PRD 写启动后改范围需新任务；影响是“**脱离上下文阅读时可能把执行中改范围理解为原任务重确认**”。补上“启动前 / 启动后”限定，正是针对该影响的定向修复。
2. **落实评审给出的最小修复方向**。同一行“最小修复与建议负责角色”列原文建议：“**产品在方案该处补一句‘启动前重确认；启动后创建新任务’**”。本建议与该方向一致。
3. **不改变 PRD 规则，只让方案与 PRD 对齐**。真实机制在 `prd.txt` `[section-4]` 第 98 行已写明：“计划启动后如要变更竞品、维度或来源范围，应复制配置创建新任务，不在原运行中静默替换。”本建议把这一既有规则在方案的同名位置补齐，**不新建规则**。
4. **消除状态机上的落点矛盾**。`design.txt` `[section-3]`（第 109–119 行）与 `prd.txt` `[section-3]`（第 86–97 行）的状态转换表中，从“执行中”出发只有完成、暂停、整体阻塞、取消四类转换，**没有“执行中 → 重新确认”的路径**；原句“改动范围后须重新确认”在状态机上无法落地。“启动前限定 + 启动后新任务”使该句与两张状态表一致。
5. **修复位置最小**。该表述在全部输入材料中仅此一行，且改动只落在同一单元格内，不牵动相邻页面说明、状态表或 `FR`/`AC` 文本，便于产品快速确认。
6. **交付整理侧已把它列为冻结前应修正项**。`handoff.txt` `[section-5]` 第 81 行：`OPEN-05 / R-05`「启动前/后改范围规则文案」｜是否阻塞正式交付：`否，但应在冻结前修正`｜关闭条件：`方案与 PRD 文案一致`。本建议的完成标准即“方案与 PRD 文案一致”。
