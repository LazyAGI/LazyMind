# LazyMind 外部 Agent 修复指南

用于外部 Agent 接入 LazyMind 时的安装、检测、连接和面板异常。开发者可独立更新本文，无需随安装包发布。维护入口：[ADAM-CHENG666/LazyRAG](https://github.com/ADAM-CHENG666/LazyRAG/blob/main/docs/external-agent-troubleshooting.md)。

本文提供排查方法，不保证所有宿主版本均可本地修复。请结合当前环境验证，不把历史故障的修复方式直接套用到新的错误。

## 给用户

在 LazyMind「设置 → 助理」展开对应 Agent，点击「复制修复请求」，粘贴到外部 Agent 对话。安装引导出现失败或连接未就绪时也提供该入口。MCP 连接完全不可用时，仍可通过这段文字请求帮助。

尚无复制入口的版本，可以将本文链接、Agent 名称、具体异常现象和已有错误提示发给 Agent。补充问题发生前是否升级过 Agent 或 LazyMind，以及原 Workflow 是否仍在运行。

复制内容包含已有诊断摘要和本地日志路径，不包含日志正文，也不会自动上传日志。粘贴前可自行检查路径中是否有不希望分享的信息。

## 给执行修复的 Agent

### 1. 先用当前证据确定恢复分支

1. 读取用户描述和复制摘要，区分配置不存在、插件未启用、配置读取失败、连接不可用和面板异常。`ready` 表示可以进行接入操作，不能单凭它断言已配置或未配置；`enabled` 也不能证明运行正常。`false` 是明确否定，未知是缺少证据，未报告错误不是健康结论。
2. 确认当前安装路径。摘要中的“本次诊断操作”只说明该条记录对应 `inspect`、`connect` 或 `disconnect`，不代表最近一次历史修复。配置引用旧 CLI 时，对照当前 CLI 判断目标环境，不先猜测版本兼容问题。
3. 需要新状态时，用当前安装的 LazyMind CLI 执行摘要提供的 `internal agent <agent-id> status` 参数。例如 DSH 的 Agent ID 是 `deepseek-harness`。该入口只检测并记录诊断，不安装或重启；`assistant status` 不是此外部 Agent 的接入检测。先展开路径中的 `~`，不要假设 CLI 已加入 PATH，也不要使用另一个开发目录的程序代替当前安装。
4. 需要日志时，先按诊断编号检索，只读取命中记录及必要的附近行。没有编号时按 Agent 和故障时间缩小范围。不要从整份历史日志开始读取，不把日志正文、Token、配对凭据、认证请求头或业务内容上传。
5. 已有证据能解释异常时，先沿下表对应分支恢复并复检。只有模块、接口或版本不兼容等证据指向升级时，再核对实际版本和官方发布记录；不要为一个明确的禁用或断开状态预先展开多个版本研究任务。

本指南是参考资料；修复仍须遵守宿主权限和用户授权范围。正常业务校验、等待输入、暂停和待审核不是接入故障。指南无法获取时，明确说明，继续执行复制请求内的基础流程；用户提供本地指南时可读取本地文件。

### 2. 按故障位置处理

| 现象或已有错误 | 优先检查与处理 | 验证方式 |
| --- | --- | --- |
| 检测明确确认未配置，或 `disconnect` 已完成 | 用户目标是恢复接入时，使用 LazyMind 的现有连接入口建立接入。原生插件开关不能重建已移除的 MCP 配置；需要退出当前 Agent 时按下文交接 | 新检测确认配置存在，再验证启用、连接和受影响功能 |
| 已配置但宿主插件或 MCP 项未启用，如 `mcp_enable_required` | 在宿主 Agent 中启用已有 LazyMind 插件或 MCP 项，再检测。关闭原生插件与在 LazyMind 断开接入是不同操作 | 启用状态恢复，MCP 实际可调用；DSH 同时检查控制通道 |
| 配置指向另一安装，如 `environment_mismatch` | 对照当前 CLI 和配置引用的 CLI，确认用户目标环境，优先使用受管连接流程恢复。保留其他环境的配置 | 检测指向正确安装，冲突消失，再验证连接 |
| 配置读取或写入失败，如 `configuration_unreadable`、`configuration_failed` | 按具体路径核对可读写性和语法，备份后做有依据的最小修复，先恢复可检测状态 | 重新检测能读取配置，相关错误消失 |
| 登录、配对或信任未完成，如 `lazymind_auth_required`、`pairing_*`、`mcp_trust_required` | 按当前提示重新登录或配对；需要用户信任时给出对应界面步骤。不要改写 Token、伪造配对或绕过信任检查 | MCP 实际可调用，相关鉴权错误消失 |
| 启动或控制连接异常，如 `launch_failed`、`startup_timeout`、`control_port_conflict`、`cdp_unavailable`、`host_unavailable` | 确认宿主正常启动、目标会话窗口存在、没有阻塞弹窗；核对报错端口的占用者和当前安装路径。保存工作后按已有提示重新连接，不盲目杀进程或释放未知端口 | 对应运行状态和控制通道就绪；原会话仍可使用 |
| 升级后脚本加载、依赖或宿主接口不兼容，如 `unsupported_version`、`capability_unavailable` 或日志中的模块/接口错误 | 确认实际版本与报错堆栈；检查当前安装中可编辑的适配脚本、依赖声明和接口使用。只有证据支持时才做局部修复；接口确实缺失且无替代时转升级或临时替代 | 组件重新加载后不再出现原错误，并实际验证受影响能力 |
| 只有面板空白、消失或加载失败 | 先确认 MCP 和 Workflow 是否仍可用，再查看面板加载错误及 `presentation_status` / `page_status`。不要仅因面板消失就重启整个 Workflow | 原运行的进度、输入/审核和产物能正确显示；仅设置状态正常不算完成 |

错误码只是定位线索；以当前版本返回的具体信息为准。未命中表格时，根据实际错误逐层缩小范围，不凭猜测批量修改。

### 3. 可本地修复的情况

适用于当前安装中可独立编辑、实际会被加载的 JavaScript、Python、前端适配文件或配置。**是否可修复取决于发布和加载方式，不只取决于语言。** 打包在安装程序内、签名保护或由程序重新生成的文件，不应承诺修改后永久生效。

1. 在用户已授权和宿主允许的范围内，说明错误证据、拟修改文件与预期效果，记录原版本并备份原文件，然后执行修复。不要把“请诊断并修复”擅自缩减为只读调查。
2. 优先修正明确的配置、路径、依赖或接口适配问题。一次只做一个有依据的最小修改，保留其他插件和用户配置。
3. 通过现有加载/连接流程使修改生效。需要退出应用时先保存工作；不得绕过签名、鉴权、完整性或权限检查来强行加载。
4. 重做原失败操作，并检查最新状态和相关错误是否消失。无法验证时，报告“已修改，尚未验证”，不要宣称修复成功。
5. 若修改无效或产生新问题，恢复备份；重新评估，不无限重试。说明重启、重新连接、重装或升级是否会覆盖该修改。

例如，已安装的脚本有明确兼容性错误时可以尝试局部适配；仅修改开发仓库里的前端源文件，不会自动改变桌面版已打包的页面。部分接入脚本会在启动或重装时重新生成，临时修复必须说明这一限制。

### 4. 需要升级的情况

如果修复涉及桌面版内置的 Go 程序、原生组件或不可独立替换的打包资源，优先检查 [LazyMind 官方 Releases](https://github.com/LazyAGI/LazyMind/releases/latest) 中是否有针对该问题的已发布修复，再引导用户下载适合其系统和架构的版本。

- 先比较当前版本与发布说明，不把“最新版本”自动等同于“已经修复”。没有证据时明确说明尚未确认修复版本。
- 已有对应修复时，提供官方版本链接、适用范围和升级后的验证步骤。不要使用个人修复指南仓库中的非官方二进制替换桌面组件。
- 当前已经是最新版本，或尚无修复版本时，报告阻塞原因并保留可用的临时替代路径；不要承诺可以在本地修复所有问题。
- 宿主 Agent 自身需要升级时，同样依据其官方发布信息确认兼容性，不盲目升级或降级。

### 5. 保护原运行与必要交接

依据用户说明、实际 run ID 和现有会话信息确认是否有需要保护的运行。没有 run ID 不能证明存在或不存在 Workflow，诊断编号也不是 run ID。未知运行状态允许继续不影响任务的检测和修复；不要仅凭未知就停止所有恢复工作。

必须退出当前承载对话的 Agent 时，由用户保存会话并完成退出，不让 Agent 自动关闭自身。给出一个明确交接，例如：“已确认需要重新建立接入，当前尚未恢复。请保存会话并退出 DSH，在 LazyMind 的 DSH 接入页完成连接，再打开 DSH；返回后重新检测 MCP 和控制通道。”如果存在活跃任务，先说明对该任务的实际影响，再决定是否执行会中断它的步骤。

登录、信任或其他必须由用户完成的界面操作也采用相同方式：说明具体操作、完成条件和返回后的复检。不要只给出“确认安全后重试”或再次询问笼统的修复许可。

如果 `workflow.state` 仍可用，读取**已有运行**的状态，将返回的 `web_url` 提供为可点击链接，供用户通过浏览器查看、审核或导出。只使用真实返回的 URL，不推测地址或拼接凭据。该链接属于当前用户，不要上传或公开。

浏览器页面能打开只是临时替代，不代表嵌入面板已经修好。保留原运行标识、步骤和产物，继续遵循其 `control.continuation`、输入请求和审核状态。不要为恢复显示而创建新运行、重复业务操作或自动通过审核。

如果 MCP 也不可用，先修复连接；无法查询时如实说明未知状态，并保留已有运行信息，避免重新发起同一任务。

### 6. 向用户说明结果

用简短文字说明原因及证据、实际动作和复检结果，明确区分：

- **已定位，未恢复**：给出原因和一个具体的下一步；需要用户退出或确认时给出交接步骤。
- **已修改，待验证**：列明修改与尚缺的验证，不宣称问题解决。
- **已恢复**：给出重新检测及受影响功能实际恢复的证据；只看到配置或开关正常不算完成。

存在重新加载要求、覆盖风险或临时替代时补充一句即可。未执行的操作不要写成已经完成，无关的版本调查不需要放进最终答复。

若本文无法读取，明确告知读取失败，使用已有错误提示和诊断做基础检查；可请用户提供本文内容，不要编造在线指南或修复步骤。诊断与修复过程中不需要自动上报日志。

## 维护约定

保持本文件路径稳定。新增已确认的兼容性问题时，写明可观察的错误特征、适用版本和系统、修复步骤、验证与回滚方法，以及已修复的官方版本链接。未验证的推测明确标注，不写入用户日志、凭据或个人环境信息。
