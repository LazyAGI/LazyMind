# PPT 模板、直接编辑与稳定版本 Dev 方案

## 1. 目标与约束

本次开发在现有 LazyMind Workflow、Artifact、聊天附件和文件预览能力上完成，禁止为了 PPT PRD 新建第二套上传、预览、版本或刷新状态机。

目标分成两条互不混用的路径：

1. **生成路径**：聊天澄清 → 可选上传 PPTX 模板 → Workflow 自动执行 → 最后一步先分析模板，再沿现有生成器产出 Deck；原生模板版式迁移在生成器具备能力后接入。
2. **直接编辑路径**：用户上传或打开已有 PPTX → 右侧 Artifact 面板预览 → 通过确定性工具换字体、调色或套模板 → 保存为新的可编辑 PPTX 版本。

每个 Deck 必须只有一个权威源：

- `html_deck`：现有无模板 Workflow 生成物，编辑 HTML 后再导出 PPTX。
- `native_pptx`：用户上传、模板生成或直接编辑得到的 PPTX，后续编辑直接修改 PPTX，不能回写到一份并行 HTML 副本。

## 2. 现有能力审查

| 需求 | 现有能力 | 结论 |
| --- | --- | --- |
| 右侧预览全部 PPTX | Chat 已有右侧 `ArtifactPanel`；`FileViewer` 已有 `pptx-preview` renderer；上传文件和发布产物都会进入 Artifact 列表 | 合理，直接复用；只补默认选中、操作入口和状态提示，不创建 PPT 专属侧栏 |
| 刷新/重进不重新生成 | Artifact 和 Workflow Session 均为服务端持久状态；Artifact revision 不可变；当前 revision 与历史 revision 已有 UI | 合理，补回归测试和幂等约束，不新增版本表 |
| 单页/单步骤重试 | Workflow 已有 step attempt、slot revision、page list index 和局部编辑工具 | 合理，继续使用 scoped rerun；禁止刷新整套 Deck |
| 换字体、调色 | 已有 PPTX 确定性编辑工具、附件 Artifact 发布和版本能力 | 合理；原生 PPTX 编辑发布新 revision，不进入整套生成 Workflow；HTML Deck 在生成后通过局部工具修改 |
| 上传/检查字体 | 系统字体可查询；当前没有用户字体库 | 部分合理。第一阶段支持系统字体检测和明确报错；字体文件上传/安装作为用户级资源能力，不能静默替代字体，也不能把字体写进 Workflow 状态 |
| 套用目标模板 | 已有 PPTX 上传、解析和 Artifact；没有原生模板分析/版式迁移工具 | 合理但复杂。先实现模板画像与受控适配；保留内容、顺序和可编辑性，不承诺像素级复刻 |
| 启动问题里上传模板 | AskCard 只有 text/boolean/single/multiple，但聊天已有成熟分片上传和附件传输 | 合理。增加通用“条件附件”元数据并复用现有上传器；不新增 `file` 问题类型和另一条上传 API |
| 快速/完整/分步确认 | Workflow 已有 auto/human step，但 PRD 不再需要逐步确认 | 合理。问题保留“生成方式”，选项仅为“快速生成”“完整生成，耗时较长”；所有生成步骤自动推进 |
| 最后一步先分析模板 | Workflow package 已支持显式 tool 列表和顺序提示 | 合理。`generate_ppt` 第一个函数调用固定为 `ppt_analyze_template`；分析不是独立 step |
| HTML → PPTX | 现有无模板链路和导出能力成熟 | 保留为 `html_deck` 路径。模板生成和已有 PPTX 编辑不得在 HTML/PPTX 间往返 |

## 3. 不做的框架改造

- 不新增 PPT 专属 Workflow 引擎、版本表、刷新恢复服务或文件上传接口。
- 不把字体替换、单纯调色放进生成 Workflow。
- 不新增“分步确认”生成方式，也不依赖用户逐步点击继续。
- 不在刷新、重新进入、轮询或预览失败时调用生成工具。
- 不让失败中的 draft 自动成为 current，不覆盖用户上传的原文件。
- 不为模板 Deck 同时维护可编辑 HTML 和 PPTX 两个权威副本。

## 4. 设计

本节包含目标设计，不代表全部已实现；本版本实际交付状态以第 8 节为准。

### 4.1 通用条件附件问题

在 `runtime.clarification_fields` 的既有 choice 字段上增加可选 `attachment` 元数据：

```yaml
- id: template_mode
  type: single
  choices:
    - 不使用模板
    - 上传 PPTX 模板
  attachment:
    when_choice: 上传 PPTX 模板
    material_id: template_pptx
    accept: [.pptx]
    max_files: 1
    required: true
```

实现原则：

- 问题类型仍然是 `single`，避免修改 Ask 的基本回答模型。
- AskCard 仅在命中 `when_choice` 时展示上传按钮。
- 上传复用 `ImageUpload`/chunk upload；已上传文件随回答消息进入现有 conversation attachments。
- Workflow trigger 继续使用现有 external file `input_bindings`，以精确文件名绑定 `template_pptx`。
- 条件附件是通用能力，可用于文档模板、数据源文件等，不在 Host 里判断 workflow id。

### 4.2 Workflow 自动生成

启动问题保留：主题、页数、受众、视觉风格、AI 底图、模板方式、生成方式。生成方式只有：

- `快速生成`
- `完整生成，耗时较长`

两种方式均自动到最终结果：

- 快速生成：跳过三套风格预览和人工页提示词确认，尽量减少额外生成阶段。
- 完整生成：保留研究、素材、三套风格候选（自动采用推荐项）、底图、完整排版和校验，但不暂停等待逐步确认。

`generate_ppt` 的新模板分支：

1. 第一调用 `ppt_analyze_template(template_pptx)`，生成可缓存的 `template_profile.json`。
2. 读取母版、版式、页面尺寸、主题字体、主题色、背景和占位符画像。
3. 使用现有内容大纲生成/适配原生 PPTX。
4. 执行溢出、遮挡、对比度、缺失字体和页数检查。
5. 通过现有 Artifact publisher 发布最终 `.pptx`，再提交 Attempt。

无模板分支继续调用现有 HTML 生成与导出，避免无收益地重写成熟链路。

### 4.3 直接 PPTX 编辑

直接编辑以一次 Artifact action/确定性 tool call 为一个新 revision：

- `inspect_fonts`：列出 Deck 使用字体、系统可用性和缺失字体。
- `replace_fonts`：指定源字体替换，或整套统一字体；保留内容、字号、粗细、段落和几何位置。
- `replace_palette`：替换主题色和显式颜色；保留透明度并做对比度检查。
- `apply_template`：在尽量保留原对象的前提下应用目标模板的主题、背景和布局画像。

执行约束：

- 必须携带 `base_revision_id`；head 已变化则返回 revision conflict，不能静默覆盖。
- 先写 draft，校验成功后才 publish；失败 draft 不替换 current。
- 输出新文件名和新 revision，原上传文件保持不变。
- 所有文字、图片、图表尽量保留为 OOXML 可编辑对象；不允许为了套模板把整页栅格化。
- 目标字体不可用时返回可操作错误和可用字体建议，不做系统默认字体回退。

### 4.4 右侧预览与当前版本

复用 `ArtifactPanel`：

- 上传或生成 PPTX 后自动选中最新 current revision。
- 顶部明确展示文件名、`vN`、来源（上传/生成/编辑）和 current 标记。
- 操作区展示“换字体”“调色”“套模板”；操作结果仍回到同一 Artifact 版本链。
- 刷新只重新读取 Artifact/Revision；预览器错误只允许重试加载文件，不允许触发生成。

### 4.5 版本与刷新不变量

1. `GET`、页面刷新、重连、SSE resume 和预览 reload 必须是只读操作。
2. 全量再生成必须来自用户明确动作，并创建新的完整版本。
3. 单页重试只发布对应 `list_index` 的新 revision，其余页沿用上一版本。
4. 单步骤重试只使该步骤及依赖它的后续步骤失效。
5. Artifact current 指针只在成功 publish 后更新。
6. 所有写操作使用幂等 key；浏览器重发不能生成两套 Deck。

## 5. 实施顺序

### P0（本分支）

- 通用条件附件元数据、AskCard 上传按钮、回答消息附件透传。
- PPT Workflow 新启动问题；移除分步确认；所有步骤自动推进。
- `template_pptx` external slot 与 `generation_mode`。
- `ppt_analyze_template`：OOXML 模板画像、缓存、明确错误。
- `generate_ppt` 模板分支的首调用约束。
- 通用 `edit_presentation`：PPTX 字体检查/替换与精确色值替换，成功后发布新的可编辑 PPTX Artifact，原文件不覆盖。
- 目标字体系统可用性校验和明确报错；不做静默默认字体回退。
- 编译器、Python normalizer、AskCard 和模板分析测试。
- 版本/刷新相关现有行为回归测试，不新建版本系统。

### P1

- 原生 PPTX 生成/模板适配器和版式映射。
- Artifact action UI：字体检查/替换、调色、套模板。
- 确定性 `apply_template`：母版、背景和布局迁移，并补齐溢出/遮挡视觉校验。
- ArtifactPanel 的 PPT 操作区、current version 信息和编辑状态。

### P2

- 用户级字体资源上传、授权和复用。
- 复杂图表、SmartArt、嵌入对象的高级适配与更完整视觉 QA。

## 6. 验收与测试

- 选择“不使用模板”时不显示上传控件，可直接提交。
- 选择“上传 PPTX 模板”时显示仅接受 `.pptx` 的按钮；上传完成前不能提交。
- 回答消息带上模板附件，trigger 将其绑定到 `template_pptx`。
- Workflow 启动后不出现逐步确认；快速和完整模式都自动到最终产物。
- 有模板时 `generate_ppt` 的第一工具调用是 `ppt_analyze_template`；无模板时不调用。
- P0 模板画像会更新现有 HTML Deck 的主题字体、主题色，并记录页面尺寸与布局提示；尚未保证生成器实际采用模板尺寸，也未完成原生母版/版式迁移。
- 刷新、重进、SSE resume、预览 reload 不增加 step attempt 或 artifact revision。
- 单页重试只改变目标页 revision；全量重生成必须有明确用户动作。
- 字体不存在时明确失败；成功替换不改变文本、字号层级、粗细、位置和段落格式。
- 新版本可预览、可下载、可继续编辑；原文件和历史版本仍可访问。

## 7. 风险

- PPTX 模板并不是简单 CSS 主题。任意源 Deck 到任意目标版式不可能保证像素级一致；验收应以内容完整、对象可编辑、风格大致相似、无明显溢出遮挡为准。
- 浏览器 PPTX 预览和 PowerPoint 原生渲染可能存在字体/图表差异，因此服务端校验不能只依赖截图。
- 用户上传字体涉及许可和跨主机安装。P0 仅做可用性检查；后续字体库必须保持用户隔离并记录许可提示。

### 8.1 科研 PPT 制作

已完成或可复用：

- 现有 PPT Workflow 有材料读取、内容大纲、逐页生成和导出链路，可作为论文、阅读心得输入的基础；这不是本次新增的科研专用能力。
- 本次新增的可选模板上传与最终生成步骤内的模板画像分析，可供科研场景复用。
- 本次保留“快速生成 / 完整生成，耗时较长”问题，并将生成步骤配置为自动推进；完整模式保留材料收集和三套风格候选，自动沿推荐项继续。
- 新增 `analyze_academic_sources` 自动条件分支：科研汇报、论文解读、学术答辩、阅读心得先整理材料，再提取研究问题、方法、证据、局限和公式/图表清单；多论文保留逐条来源归属。`academic_brief` 接入现有大纲步骤。
- 科研启动 Ask 增加条件材料问题：只在科研任务缺少论文附件、研究正文和阅读心得时询问，复用已有材料；支持 PDF/DOC/DOCX/TXT/MD，不限制文件数量（max_files=-1）。PPTX 模板仍限制 1 份。可选 Other 输入研究内容/阅读心得，不强制上传。`ask_when` 复用启动阶段模型语义判断，并非独立的确定性场景分类器。
- 多文件沿用普通聊天附件传输，并在启动请求保留所有精确文件名。现有启动器只支持单文件绑定，因此多文件不伪装成单个文件绑定；科研工具按会话附件逐篇解析。PPTX 模板单独绑定，不作为论文源。
- 新增 `ppt_cache_academic_sources`：调用共用 reader，按 next_offset 逐段读到 EOF；结果保存到用户/会话隔离的 academic_sources 目录，按源文件 SHA-256 缓存完整 reader chunks。相同内容复用、文件变化重新解析、单篇失败明确返回且保留其他成功结果。`ppt_read_academic_source` 按块读取缓存，不重新解析；manifest 保存文件名到 source_id 的对应关系。
- 公式采用带编辑锚点的 HTML/MathML，科研代码图采用内联 SVG；点击后通过既有 Chat 预览/提交链路局部修改，保持源文件哈希校验。仅允许被动 HTML/MathML/SVG，不执行模型返回的任意 JavaScript。
- 图片内容修改调用已有 `image_editor`；未配置时明确提示模型设置入口。文字、公式和代码图修改不要求图片编辑模型。图片编辑质量取决于所配置模型，不能保证其科学数据准确性。
- 科研模板复用现有 PPTX 模板上传及分析，不新建模板流程；长公式通过提示约束有意义分行、专页、变量说明及可读性，效果取决于生成模型。

明确不采用的方案：

- 不另建科研专属 Workflow 引擎；科研模板、页面结构和内容展示在现有 PPT Workflow 内扩展。
- 不把“普通 PDF 可以读取”直接当作“单篇/多篇论文与科研场景已经验收通过”。

尚未完成：

- 独立科研内置模板库本轮不做；按用户要求复用上传模板。场景叙事已进入科研分析提示，真实页面效果待验收。
- 自己的论文、单篇论文、多篇论文、阅读心得四类输入的实际端到端验证；多论文综合、引用归属和图表提取质量验证。
- 公式 HTML/MathML 的交互编辑已实现；PowerPoint 原生可编辑公式（OMML）及各种复杂公式导出保真未实现，需单独验证现有导出结果。
- 科研图表、图片、标题、正文在预览与导出中的视觉验收，以及长公式/高密度内容的排版调优。

### 8.2 支持 PPT 换字体和套用模板

已实现：

- 2026-10-17：上传模板时固定 `style_flow=auto`、AI 底图关闭，跳过三套风格候选、底图提示词和底图生成；启动 Ask 对已选择/上传模板的任务不再询问视觉风格与 AI 底图。分析后校验拒绝模板与底图开启的冲突配置，且不检查文生图模型。完整模式仍保留材料收集/科研分析。模板画像继续在最终生成步骤执行；现有 HTML 基础样式准备与导出链路继续复用。
- 本地统一字体库：`LAZYMIND_FONT_DIR` 指定共享绝对路径，默认 `~/.local/share/lazymind/fonts`。每个字体保存内容哈希 ID、TTF/OTF 文件、家族/别名、字重、样式和许可元数据；算法和 Node 导出服务读取同一目录。存储边界已留 TODO，后续可接云对象存储及本地缓存。
- 管理员可运行 `python algorithm/lazymind/chat/engine/tools/file_resources/font_library.py import <字体路径>` 导入，`list` 查看。变量字体导入为静态常规字重实例；当前开发机已从仓库现有 Noto Sans SC 导入 400 字重，字体库文件未提交 Git，部署环境需执行同样初始化或挂载共享目录。
- 字体替换检查包含本地字体库；HTML 预览按使用情况嵌入字体 CSS，导出浏览器加载同一字体，HTML→PPTX 优先嵌入本地字体并沿用已有 EOT 许可检查。没有嵌入许可的字体不会作为可分发字体使用。原生上传 PPTX 的直接编辑暂未新增字体嵌入。
- 普通聊天注册 `edit_presentation` 工具，支持 `inspect`、`replace_fonts`、`replace_palette`；简单编辑无需进入生成 Workflow。
- 检查 PPTX 字体引用和执行工具所在系统的字体可用性；替换指定源字体，或统一替换显式及主题字体引用。目标字体不可用时返回错误。
- 原生 PPTX 字体替换支持整套、指定 1-based 页面，以及 `all`、`titles`、`body` 三种文字范围；指定页按演示文稿实际页面顺序解析，只改对应页面 OOXML，不改其他页或主题。
- Workflow 已生成的 HTML Deck 支持整套或指定页面、全部文字或标题/正文的确定性字体覆盖；修改后立即重新发布对应预览。整套修改同时更新 `style_spec.json`，使后续页面生成和现有 HTML→PPTX 导出沿用新字体；局部修改不污染全局样式。
