# 通知前端与 HTML 原型复核（2026-09-17）

## 结论与检查范围

当前实现具备主要通知能力，但交互与展示尚未完整对齐原型。新建定时任务的通知草稿是明确的功能缺口，不能视作纯样式差异。

依据是用户本次提供的四份 `lazymind-*.html` 文件。四份均包含新建任务、通知编辑、全局设置和连接管理代码；默认入口不同。逐项读取实际渲染及事件处理代码，并在当前 Local 页面打开新建定时任务、消息通知、终端连接进行核对。未创建任务、变更通知规则或连接外部账号；未重做已成功的 Safari 通知验收。

## 确认的差异

| 优先级 | 位置 | HTML 原型 | 当前实现 | 修正涉及范围 |
| --- | --- | --- | --- | --- |

| 中 | 定时任务卡片 | 卡片直接提供“配置通知”，进入通知编辑 | 入口藏在更多菜单内，点击先打开任务详情，需再点“配置通知” | 前端入口及抽屉状态复用 |

| 低 | 新建表单文案和时间控件 | “新建定时任务”/“创建任务”；每个工作日/每天/每周及时间 | “新定时任务”/“创建”；每 N 周等既有控件，时区显示实际本地名称 | 文案可对齐；需保留既有时间能力，不能为了外观缩减支持范围 |

## 新建界面已经对齐的部分

920px 弹窗、任务/任务组选择、任务名称、500 字任务描述、备注、最多三个附件、资料库、执行时间、加入任务组、依赖任务等均存在。资料库因未配置 Embedding 显示不可用属于真实能力状态，不应照抄原型中的可选演示知识库。依赖任务支持多选，属于既有能力，应保留。

## 接口与组件依据

- `frontend/src/modules/taskCenter/ScheduleList.tsx`：新建表单、创建/更新 payload、卡片入口；新建只显示提示，编辑使用独立 ScheduleNotificationPanel。
- `frontend/src/modules/taskCenter/api.ts`：CreateScheduleRequest 无通知配置字段。
- `backend/core/scheduler/scheduler.go`：创建请求同样不接收通知配置；不能靠前端增加字段解决。
- `backend/core/taskcenter/notification_handlers.go`：单任务配置拒绝 config=null；当前没有清除为未配置的公开行为。
- `frontend/src/modules/notifications/{NotificationSettings,RuleEditor,ScheduleNotificationPanel}.tsx`：设置/任务共用固定顺序编辑器、详情摘要与确认逻辑。
- `frontend/src/modules/channelGateway/pages/ChannelConnectionPage.tsx`：已有两列连接页和真实账号信息，缺返回使用账号的交互衔接。

## 需要保留的已确认行为

- 企业微信采用用户已确认的智能机器人 BotID＋Secret，不复制原型通用扫码演示。
- 微信保留既有 ClawBot/iLink 接入及会话约束。
- 浏览器权限、系统通知与 Desktop 原生通道按已实现能力保留；原型静态“已授权”不能替代真实权限判断。
- 未配置的旧任务不自动开启通知；默认规则仅作用于新任务，单次执行使用规则快照；通知失败不改变任务结果。
- 系统通知正文有长度限制，外部渠道按已支持的摘要/全文契约展示，不把原型内部遗留的格式示例当作新增生产能力。

原型说明文字仍有“配置/移除、不使用渠道开关”的旧描述，但本次 HTML 的实际 taskChannelGrid 已渲染开关。对齐应依据本次实际界面和用户已确认行为，不能反向改回旧说明中的交互。

## 建议实施顺序及验收

1. 优先补齐新建/编辑通知草稿和原子保存，复用现有通知校验与事务；分别验证 SQLite/PostgreSQL。不得采用先创建再补配规则的两次请求冒充一次成功，避免首次执行抢跑及部分保存。
2. 调整配置入口、设置/任务两种布局、内嵌账号选择、详情摘要和平台标识；复用 RuleEditor 与现有连接组件，不重写相同逻辑。
3. 完成连接后带回账号、设置往返保留草稿、准确的运行中确认；清除配置需保持历史和运行快照不变。
4. 验收覆盖创建前配置、取消不落库、最终保存原子性、异常保留草稿、旧任务不初始化、账号切换不影响其他任务；逐页人工核对布局并回归既有浏览器/Desktop 通知。
