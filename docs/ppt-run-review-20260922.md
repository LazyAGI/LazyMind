## 4. 素材为何慢

### 4.1 注册 3 张图片用了 110.308 秒

`ppt_register_material_images` 于 10:33:00 开始，10:34:50 返回成功。源文件记录如下：

| 图片 | 文件修改时间 | 大小 |
| --- | --- | ---: |
| material_01 | 10:33:13 | 2,246,233 字节 |
| material_02 | 10:34:49 | 2,264,418 字节 |
| material_03 | 10:34:50 | 64,937 字节 |

实现中 `_stage_one_material_image` 按列表顺序串行执行，全部处理完成后才进入图片产物发布循环。结合修改时间，主要等待落在第二张处理区间，约 96 秒；这是基于串行实现和文件时间的推断，不是已埋点测得的纯下载时间。

已确认：第一张在 10:33:13 已落盘，却要等整批完成后才发布；发布记录约在 10:34:50。慢图片拖住了先完成图片的预览。

建议：有限并发下载，逐张完成后按明确索引发布，保持页面与素材映射；保留本地缓存与失败复用。补充连接、响应、下载字节数、落盘、发布分别耗时。现有 requests timeout 不等于整个流式下载的总时限，应增加总时限与取消能力。

### 4.2 搜索日志不能直接计为六次调用

日志出现三组成对、同时间同耗时的 `ppt_search_web_images`：9.798、14.906、6.334 秒。模型简报声称“6 次预算用满”，但成对事件可能来自嵌套 guard 重复记录；没有独立调用标识，不能据此断言实际发起了六个外部请求。

建议给外部搜索请求记录独立 request/call ID，预算在工具边界计数，避免依赖模型自述或日志行数判断。

### 4.3 图片槽位保存错误与重复简报

10:35:10，模型把 `material_images` 的 manifest 路径以 `content_type=file_list` 交给 `save_artifacts`，触发图片槽位校验。此前注册工具已发布图片，本不需要再保存 manifest 到图片槽。

10:35:28，再次保存成功；10:35:40 阶段结束。错误到成功相隔约 18 秒，不是失败工具执行了 18 秒（失败调用只有 0.005 秒）。截图中同时出现两份 `material_summary`，与先保存摘要、后续图片项失败、再次保存摘要的过程吻合。该因果仍应通过产物批处理事务行为进一步核实。

建议：注册工具明确返回“已发布，不要重复保存图片槽”；批量保存前先验证整批类型，避免前项成功后项失败造成部分提交；摘要使用稳定标识覆盖或幂等保存，不靠重复追加。

## 6. 大纲本次没有“几分钟全在生成”

### 当前大纲与最后一步的实际边界

目前移到最后一步的是视觉样式与渲染规则，并不是全部结构化大纲。`ppt_build_outline` 仍执行 preflight → content-outline → 发布 Markdown：模型生成每页标题、要点、页面类型、简短视觉提示及素材绑定，返回 `pages` JSON，再进行格式规范化、页数/字段校验和必要的局部纠正。这部分本次用了 46.278 秒。

因此，如果预期是“大纲阶段仅给用户一份简洁的内容大纲，内部页面 JSON 结构也到 generate 再形成”，当前实现尚未达到这个边界。不能把“样式已后移”表述成“大纲结构全部后移”。进一步调整需要同步处理每页提示词、用户编辑和素材绑定的消费接口，避免末步重新规划导致已确认内容改变。

- 阶段：73.708 秒。
- `ppt_build_outline`：46.278 秒（10:38:37—10:39:23）。
- 剩余约 27.4 秒是工具外的阶段开销，包括查找 deck 前后的等待、取回产物和收尾。
- 日志只观察到一次外层 `ppt_build_outline`；它内部是否触发纠正，当前汇总日志没有打印 attempts，不能把“一次外层调用”写成“一次模型调用”。

当前文件和调用顺序符合之前的调整：大纲先完成，统一样式在 generate 阶段生成。性能评估应同时看 outline 和 generate，不能只把耗时转移到后者就认定总耗时优化。

建议记录大纲内部 attempts、每次模型调用耗时、输入输出 token 和本地校验时间。保留本地规范化及局部纠正，不恢复整链重跑。

## 8. 图片先不显示、后又显示

用户先观察到右侧和主面板未显示，后来右侧显示、主面板仍“处理中”，最终全部显示。因此本次结果是“最终加载成功，存在可见延迟”，不是“图片损坏或永久请求失败”。

已确认两处走不同前端逻辑：

- 主面板 `SlotComponents.tsx` 的 `useSlotImageUrl` 先解析地址并预加载，成功后才展示。
- 右侧 `TaskCenter/index.tsx` 的 `ArtifactGrid` 直接交给图片组件加载。
- 主面板预加载没有独立超时；失败重试耗尽后 `url` 仍为空，而 `SlotImage` 继续展示“处理中”。这是代码中的潜在状态表达问题，不是本次已经证实发生的失败。

后端发布记录不能证明浏览器已经收到、解码并显示。此次没有浏览器 Network/HAR 或加载事件埋点，无法量化发布到显示的延迟，不能武断归因于 Base64、签名失效或网络请求失败。

建议统一两处图片资源解析和缓存；记录签名请求、图片请求、onload/onerror、重试与组件挂载时间；区分“待生成”“加载中”“加载失败”，失败提供重试。缩略图使用约定位置的缓存，避免每次重新截图；这不等于要求所有图片都转 Base64。
