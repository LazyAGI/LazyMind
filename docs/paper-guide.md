# Paper guide

The paper guide opens alongside the [original PDF reader](pdf-formula-reading.md) for PDFs in academic paper libraries. It explains one paper as a continuous article with an outline and four roles: **background** establishes what the reader needs to know, **question** identifies the problem or gap, **contribution** explains what the authors add, and **justification** walks through the reasoning and evidence that support it. Section titles and explanations follow the paper's argument. For example, a theory paper may need a walkthrough of assumptions and proof dependencies, whereas an observational paper needs a distinction between association and causal identification. Mixed or unclear argument types are allowed. The guide labels paper paraphrases, interpretations, teaching explanations, hypothetical examples, and external background separately.

## Open and read a guide

1. Open an original PDF from an academic paper library and choose **Guide** (导读) next to **Original** (原文). The Guide tab is hidden when the deployment disables the feature and you have no saved revision for this paper and language. To create a guide, the deployment and your [reading preferences](pdf-formula-reading.md#personal-ai-reading-preparation) must allow generation. The reader uses Chinese when the interface language is Chinese and English otherwise; the two languages have separate revisions.
2. Choose **Generate paper guide**. If the PDF has no usable structure yet, choose **Prepare paper and generate guide**. Preparing the structure requires the necessary permissions, parsing preference, and a supported parsing service. You can read sections as they pass review, and leave and reopen the reader while generation continues.
3. Use **Compare original** to read with the PDF side by side on a wide screen or switch panes on a narrow one. A source citation opens a preview before you jump to the PDF, and **Previous source position** returns you to where you were in the PDF. The guide keeps its own reading position.

Select text within one guide block to explain the passage, request a clearly labeled hypothetical example in the assistant, or inspect its sources. Selection anchors refer to the original stored guide text in Unicode code points. When a selection intersects rendered math or a rendered guide comparison table, it includes the whole expression or table, preserving the raw expression or row and column context. Supported LaTeX renders inline or as display math; unsupported expressions remain as text. A supported comparison table renders as a scrollable grid; unsupported table text remains readable. These generated comparison tables are distinct from the paper's own tables.

Source previews show retained text and, where available, original PDF crops or formula previews. A verified physical page can support a page jump without a precise text highlight. Precise text boxes require the full passage to be verified within a physical layout region. Physical table fragments link to the pages containing their rows, captions, or notes. A cropped table preview starts on the table's first page. Image and table explanations use parsed text, table cells, captions, and surrounding passages. Original crops are for the reader to inspect; the model does not infer details from their pixels. A caption or mention alone does not establish that its asset is available, and eligibility metadata does not establish that the asset is readable, central to the argument, or correctly interpreted.

## Generation, interruption, and revisions

Use **Generation details** to see the displayed revision's model, source version, request count, and coverage. **Model for this run** overrides the model for a new generation only. Without a per-run selection, new generation uses the account's reading study model, which can itself follow the configured default. Selecting a model here leaves reading and chat settings unchanged, and existing revisions retain their generating model.

- A run can queue, wait for PDF structure, analyze the paper, write sections, and review the full guide. A **partial** candidate contains at least one reviewed section. It may still be running, paused, canceled, or failed, and a later whole-guide finding can mark a visible section as needing correction.
- A **complete** revision passes whole-guide review within the available source scope. **Limited** is also a completed result: extraction narrowed the review scope, or the frozen source coverage has warnings. See the coverage details. A budget stop, failure, or unresolved review finding does not produce a completed limited revision; any previously released sections remain readable while access is valid.
- **Cancel remaining generation** stops future local work and preserves released sections. **Resume** restarts an eligible current candidate from saved checkpoints with the same source, compatible generation contract, original model identity, and remaining budget. **Regenerate** starts a new candidate, with a fresh budget and the selected model or reading preference. Use regeneration when the source or execution contract has changed, the old model no longer matches, or the prior run cannot continue.
- The last completed published revision stays available while a replacement candidate runs or fails. A candidate replaces it only after successful whole-guide review. A reader can keep the revision already open and choose **Read new version** when the replacement is ready. Superseded revisions can still be read by revision ID with current document access. If the original or its verified positioning changes, historical guide text and retained evidence can still be read, but source jumps, highlighting, and follow-up questions anchored to that guide are disabled against the current PDF.

## Deployment and source requirements

Set `LAZYMIND_PAPER_GUIDE_ENABLED=true` in Core to enable new guide generation. It defaults to disabled when unset; a false or invalid boolean value also disables it. The flag and the personal `paper_guide` mode gate new generation and resumption. Existing authorized results remain readable. The feature is on demand, including under the advance and full reading presets. Its generation budgets are separate from the automatic preparation quotas.

The generation gate requires an academic dataset (`academic_papers`) and an original PDF. With an existing usable parse, document read access suffices to create your personal guide. Preparing a missing PDF structure requires document write access, the separate `pdf_parse` capability, and a supported configured parser. Opening the guide or reading its status starts neither parsing nor generation. The guide and its progress are private to the authenticated owner, dataset, document, and language. Reading, evidence lookups, and follow-up context still require current document ACL access. Retrieval preparation, full-document translation, and saving notes continue under their own settings and permissions.

Guide source precision is derived from the source-matched PDF IR and retained MinerU ZIP, independently of the reader's table projection. The Core precision projection currently recognizes the MinerU `3.4.4` archive producer contract for `vlm` and `hybrid`. This is a compatibility check on retained archive contents; service configuration for the existing PDF parser is described in [PDF paper reading](pdf-formula-reading.md#enable-and-use). The archive must also prove the relationship between the base IR and its layout payloads, including physical page evidence and supported table structure. Unknown producer contracts, missing archives, or inconsistent projections yield an explicit source-precision unavailable state. The guide does not automatically reparse or guess coordinates in that case. The original PDF, independently usable reader artifacts, and retained authorized guide history remain available.

Keep the PDF artifact directory and the Core database on persistent storage. The guide stores an immutable personal source snapshot beside the document's artifacts and validated generation steps in Core. Precision data is a separate immutable artifact; deriving it does not rewrite the base IR or producer ZIP. The original PDF SHA-256 and verified IR digest determine whether a revision's evidence is current. The execution fingerprint also binds the source catalog, task contract, and frozen non-secret model identity, so a saved run cannot silently continue using a different contract. Credentials and another copy of the PDF are not stored in the guide snapshot.

## Review coverage and work limits

When the full source evidence fits, planning and whole-guide review receive the source packet from before Plan selected its claims and assets. For a larger source, bounded extraction processes source packets in reading order. The independent packet retained before planning then consists of original evidence kept by that extraction and complete physical table groups. Whole-guide review and corrections prompted by it use this independent packet, so review can find problems beyond Plan's chosen citations. In extraction mode the coverage warning means some original passages may not have been checked. It does not indicate that the original is missing or waive factual and explanation defects. An abstract without usable body text is insufficient, and a source or later task that cannot fit its context limit fails explicitly. Review and provenance checks do not certify the guide's accuracy across disciplines or models; compare critical claims, equations, and values with the PDF.

| Limit | Per revision |
| --- | --- |
| Guide model attempts | 24 total: up to 8 initial extraction attempts, 14 other initial attempts, and 2 recovery attempts |
| Review corrections | At most 2 distinct target locations, with one correction per target |
| Model request timeout | Starting with `paper-guide-v13`, 180 seconds per PLAN attempt and 120 seconds per other guide attempt, subject to any earlier run deadline |
| Active work | 30 minutes across executions, including model calls and local processing (120 seconds reserved per execution); queueing and time between parser dependency checks are excluded |

An initial section review can spend both correction targets on that section if it finds two distinct problems in succession. Each draft in that chain receives its own review before publication, and whole-guide review uses the latest reviewed section. Each section request lists the exact source aliases and visual block kinds it may use for that role. Other supplied sources can still support prose.

Starting with `paper-guide-v14`, new sections keep request-local source IDs in structured citations. A draft with a clear alias citation at the end of a paragraph is rejected as invalid model output and counts toward the existing attempt limits. Literal notation and quoted source lines can keep their original text.

`paper-guide-v15` asks section writing, corrections, and review to distinguish the supplied evidence selection from the original paper. If a mechanism belongs in a later section, an earlier one can introduce it as a question. The body and summary should not turn missing support in a section into a claim that the paper omitted it. A guide can still report unavailable parser text or figure pixels when the supplied material shows that limitation. Published revisions and their selection offsets are preserved; a run with older generation checkpoints requires regeneration.

`paper-guide-v18` lists the exact argument-family values separately from attribution and support status. Each PLAN request lists the source aliases eligible for `required_assets` decisions, including exclusions. Eligibility covers supplied table evidence and the selected figure and formula candidates. Other supplied evidence can still support prose. Output validation rejects unknown values and out-of-scope asset decisions.

Starting with `paper-guide-v19`, the server sends the output schema through strict Structured Outputs for EXTRACT, PLAN, SECTION, and REVIEW when the selected model is `gpt-6-luna` or `gpt-6.1-sol` on the standard official OpenAI Responses endpoint. The server selects the format and sends the schema once. Other models and endpoints receive the schema in their prompts, with JSON mode where previously enabled. A provider rejection, refusal, or truncated response fails the attempt under the existing limits. Successful responses still need to pass JSON, source reference, and guide validation before they can be saved.

`paper-guide-v20` shows SECTION only the planned claims whose entire evidence list is present in the request. This applies to drafts, local corrections, and whole-guide corrections. If evidence is missing for a claim assigned to the requested role, the request fails before model configuration. Validation uses the complete plan, including when checking whether a new claim reuses an existing ID. Published revisions remain readable, and older revisions with saved generation work require regeneration.

The PLAN guidance in `paper-guide-v20` makes the four reader tasks explicit. The question sets up the open issue and its constraints; the contribution explains the authors' answer; the justification explains what their reasoning or evidence supports and where it stops. The plan places originals where they help explain the argument and assigns each key concept a main explanation role. This guidance applies to both schema transports.

Starting with `paper-guide-v21`, Core's context check credits only repeated structured source IDs that Python shortens to request-local aliases. The first occurrence of every ID remains charged, which covers the PLAN asset map. Core applies the original input size and evidence count limits before taking that credit. Source text, formulas, and the canonical request are preserved.

Starting with `paper-guide-v21`, section writing and each single-section review first try the full retained planning packet. The context check includes the actual request, including the plan, any continuity summary or repair findings, and the draft being reviewed. If that request is too large, Core uses the role's planned evidence and the reviewed or repaired draft's cited evidence, including every source of a cited claim and all fragments of any included table. If the smaller request still exceeds the context limit, Core stops before reserving a model attempt. Whole-guide review and the corrections it requests require the independent planning packet.

The guide worker runs at most two jobs concurrently per Core process. The database serializes guide execution for the same user, including requests for different papers or languages. A worker restart can reuse saved steps whose inputs and outputs still validate; a saved Plan also requires its original extraction checkpoints when applicable. Lease and revision checks prevent an old worker from publishing after its run has been replaced or canceled.

Each outbound attempt is reserved durably before dispatch. An interrupted attempt with an unknown outcome keeps its attempt count and time reservation. Resuming does not reset any budget, and may call the model again for work that never reached a validated checkpoint. The count describes reserved attempts and may include one whose dispatch could not be confirmed. Cancellation and local timeout do not guarantee that a provider stopped processing or billing. The limits are not a monetary cap or a guarantee of exactly-once provider execution.

A revision that stops with `paper_guide_review_required` cannot resume, including after cancellation. The reading workspace keeps the published sections and their correction warnings visible, and offers a new guide when generation is available. Ordinary cancellation and transient model failures can still be resumed if the candidate passes the existing checks.

## API

See the [Core OpenAPI specification](../api/backend/core/openapi.yml) for request and response schemas. Paths below are relative to `/api/core/datasets/{dataset}/documents/{document}`. Normal responses use the Core `data` envelope. Use `language=zh` or `language=en` on routes other than generation; generation takes `language` in its JSON body. Core defaults to `zh` when language is omitted. The routes use the existing Core authentication and document authorization, with revisions scoped to the authenticated owner.

| Method and path | Purpose and payload |
| --- | --- |
| `GET /paper-guide` | Returns availability, current PDF hash, published and candidate revision summaries, and reading progress. Supports private `ETag` revalidation with `If-None-Match` and `304`. A change to the current verified IR also changes the validator. |
| `POST /paper-guide:generate` | Send `language`, `expected_source_hash`, `idempotency_key`, `regenerate`, and optional `model_ref`. The expected hash must match the original. A new submission normally returns `202`; reusing an existing revision can return `200`. Set `regenerate: true` with a new idempotency key to request a fresh candidate. |
| `GET /paper-guide/revisions/{revision}` | Returns run state, source currentness, coverage, reviewed sections and any available plan and review summary. `after_version` restricts returned sections to changes after that revision change version. |
| `GET /paper-guide/revisions/{revision}/evidence/{evidence}` | Returns stored evidence and `source_current`. Page indices are zero-based; boxes use the PDF IR's normalized top-left coordinates. Evidence drops precise coordinates when `source_current=false`. Superseded revisions still retain their locators while their source remains current. |
| `POST /paper-guide/runs/{run}:cancel` | Cancels remaining work and preserves released sections. The run ID is the candidate revision ID. |
| `POST /paper-guide/runs/{run}:resume` | Requeues the same eligible candidate with its frozen identity and remaining budget. A saved quality stop on a candidate that passes the existing checks returns `422 paper_guide_review_required` before enqueueing work. A mismatched task contract returns `409 paper_guide_regeneration_required`. |
| `PUT /paper-guide/progress` | Saves `revision_id`, `section_key`, `block_id`, Unicode code point `offset`, and `mode` (`article` or `source`). |
| `POST /paper-guide/revisions/{revision}:selection-context` | Takes `section_key`, `block_id`, and half-open Unicode code point offsets `start` and `end` in the stored block text. Returns server-resolved text, claims, evidence, and source currentness. Assistant follow-ups re-resolve the reference with the conversation user's access and reject stale source context. |

Status and revision responses include `run.resume_block_reason` when the revision has the stored quality stop. The field is optional and conveys a known block. Resume still checks access, the source and frozen model, candidate identity, the task contract, and the remaining run budget.
